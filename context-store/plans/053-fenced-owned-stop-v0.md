# Plan 053: Fenced owned stop v0 (stop requests bound to one dispatcher launch)

**Status: independently reviewed local source.** Lead verification passed 76 focused cases with one Windows symlink capability skip. A real request using the wrong expected launch ID was refused `owner_changed` against the current live dispatcher, leaving the stop file unchanged. The author had no shell; its original unrun report and all subsequent proof remain retained at `D:/hekate-coordinator/runs/stop-fence-001/`. Runtime adoption and ChatAgent adapter integration remain separate delivery gates. Extends plan 050; module `scripts/local/supervisor_e1/e1/owned_dispatch.py`.

## 1. Defect

The chat adapter reads the owner's launch ID (A) and journals it, but `request_stop` separately re-read "any live owner" and wrote an unfenced `stop.request`. Owner B could replace A between those reads and the write, or A's request could land after B's startup archival of stale requests. Either way B, which holds the store and polls the file, would honour a request that was never meant for it.

## 2. Contract

| Concern                                       | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flag                                          | `stop --expected-launch-id <32 lowercase hex>`; optional; default `None` keeps the legacy unfenced request byte-for-byte (no `targetLaunchId`). Supplied-but-invalid (including empty) is a refusal, not "absent".                                                                                                                                                                                                                                                                                                                                                                                                  |
| Unsupported elsewhere                         | `launch`, `run`, `status` with the flag exit 2 `unsupported_flag` before any effect. `run_argv` never rebuilds it, so it cannot become the new owner's `--launch-id`.                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Native refusals (before any stop-file effect) | `invalid_expected_launch_id` (checked first, before reading status), `no_live_owner`, `owner_changed` (live owner's status `launchId` differs or is absent). Exit 2.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Accepted                                      | stop file gains `targetLaunchId`; output echoes `targetLaunchId` and says delivery and completion are not confirmed. It does not claim the owner saw or obeyed the request; read `status`.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Dispatcher check                              | A `StopGate` (the dispatcher's `stop_requested` seam, also passed to `run_plan`) judges the file on each poll: `legacy` (JSON object without `targetLaunchId`) honoured; `fenced` with `targetLaunchId == own launchId` honoured; `fenced` for another launch ignored; anything else `unknown`. A honoured request latches. A foreground `run` without a launch id never matches a fence.                                                                                                                                                                                                                           |
| Foreign request                               | ignored and RENAMED to `stop.request.foreign-<ms>-<rand>` in `<state-dir>/dispatch/` (the dispatcher owns it while holding the store); event `foreign_stop_request_ignored`, status `ignoredStopRequests`. Nothing is deleted.                                                                                                                                                                                                                                                                                                                                                                                      |
| Unknown request                               | read is bounded: `lstat` must show a regular, non-symlink, non-reparse file of at most 4096 bytes, opened `O_NOFOLLOW` where available, re-checked with `fstat`, read at most 4097 bytes; JSON object required; `targetLaunchId`, if present, must be well-formed. Otherwise `unknown` (`unreadable`, `not_regular_file`, `oversized`, `malformed`): NOT honoured (cannot be shown to target this owner), left alone for a 5 s grace (a half-written file is not judged), then renamed to `stop.request.unverified-...` with event `unverified_stop_request_ignored`. Links are renamed, never followed or deleted. |
| Evidence bound                                | at most 16 renamed files per dispatcher process; past that a request is still ignored and left in place.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Unchanged                                     | legacy unfenced stop; startup archival of a stale `stop.request` (before the first status flush); single `LocalStore` lock; native birth/heartbeat/launchId acknowledgement; all limits; graceful in-flight behaviour (the node finishes, no new claim; the gate is not consulted mid-node). No second loop, engine or force kill.                                                                                                                                                                                                                                                                                  |

Behaviour change to know about: an empty or non-JSON hand-made `stop.request` used to stop the dispatcher merely by existing; it is now `unknown` and does not. The CLI `stop` (fenced or not) writes valid JSON and is unaffected.

## 3. Residual race, stated plainly

The fence makes a stale or foreign request harmless; it does not make the CLI's own check atomic. `request_stop` can still write a request for A after A has been replaced by B (accepted output then says only "recorded for that launch"). B ignores and retains it; A is gone. If the file sits there before B's startup archival, B archives it as stale as before. A request that no live owner ever reads simply stays as evidence.

## 4. Tests (`tests/test_owned_dispatch_stop_fence.py`, offline, fakes only)

Wrong expected owner and invalid IDs create no file; accepted request stores and echoes the target without claiming delivery; legacy default unchanged; owner replaced between the precheck and the write cannot stop B; negative control (the old existence-only guard WOULD stop B, the gate does not); foreign request after B startup ignored and retained, then a correct request for B is honoured; matching request made during a node is honoured after it with no next claim; foreign request during a node stops nothing; malformed/oversized/link/directory stop files are bounded, not honoured, renamed not deleted; the read is capped at 4097 bytes; evidence cap; flag rejected by `launch`/`run`/`status`; flag absent from child argv.

Not tested here: matching-request delivery to a real owner running the new gate, a replacement-owner process race, Windows reparse points other than symlinks, concurrent writers, and the chat adapter's use of the flag. The live wrong-target precondition proof establishes refusal only; it does not establish delivery or shutdown.
